  2. Cast the chart — Swiss Ephemeris computes real placements. This is exact
  maths, no AI.
  3. Turn the chart into sentences — "Ascendant is Aries.", "Saturn is in the
  7th house."
  4. Search the books — those sentences get embedded and matched against book
  pages in a vector database. Whole pages come back, ranked by how many chart
  facts point at them and how authoritative the book is.
  5. Write the answer — the pages plus the chart go to the AI, which writes the
  reading.

  So today the AI is reading pages and interpreting them on the fly. It's a
  librarian: it finds roughly relevant passages and improvises.

  How it works once rules exist

  Steps 1 and 2 stay identical. Steps 3–5 change:

  3. Turn the chart into tokens instead of sentences —
  lord_of_house_in_house.7.6 rather than "the 7th lord is in the 6th house".
  Exact, machine-comparable.
  4. Look up rules instead of searching pages. Every rule was stored with its
  condition already broken into these same tokens. So it becomes a database
  query: give me every approved rule whose condition tokens are all present in 
  this chart. No embeddings, no guessing — a rule either matches this chart or
  it doesn't.
  5. The AI writes only the prose. It receives the matched rules — "BPHS 20.2
  says: 7th lord in 6/8/12 → spouse will be sickly" — and its job is to phrase
  that warmly in the Rishi's voice. It's no longer deciding what is true, only
  how to say it.

  The difference matters in three ways:

  - You can cite exactly. Chapter and verse, down to the character span on the
  page.
  - Wrong answers become findable. If a reading is bad you look up the rule and
  fix that one row. Today you can only re-tune a prompt and hope.
  - A human can approve rules before users see them. The database already
  enforces this: a rule is invisible unless status='parsed' and someone has
  approved it. Nothing an AI extracted reaches a user unreviewed.

  What's genuinely missing between here and there

  Three pieces, and one is bigger than it looks:

  1. The rule compiler. Extraction produces a condition as JSON. The matcher
  needs it as indexed database rows with a token on each one. That translation
  doesn't exist yet — vocab.py even has a note saying it's still to be built.
  Without it the rules sit in the database unusable.

  2. The two halves speak different languages. This is the one I'd flag hardest.
  Your chart engine currently produces English sentences because that's what
  page-search needs. The rules need tokens. Same information, different format,
  and the token vocabulary has to match on both sides exactly — vocab.py warns
  that a mismatch means "every affected rule silently matches nothing." A rule
  that quietly matches zero charts looks fine in every report and is worthless.
  So this needs a test that pins chart output against rule input, not just
  careful coding.

  3. Rules won't cover everything, so pages stay. With ~650 rules from 963
  verses, plenty of questions won't match any rule. So the flow needs both: try
  rules first, fall back to today's page search. That's a feature, not a
  compromise — but it means you're maintaining two retrieval paths, and the
  answer needs to tell the user which one it used.

  The honest sequence

  Extraction (nearly done) → fix the empty fields → run the full book → build 
  the compiler → align the chart tokens → wire rule-matching into the
  orchestrator ahead of page search → human review of the rule base.

  The extraction we've been working on is roughly the first third. The compiler
  and the token alignment are where the remaining risk sits, because that's
  where things fail silently rather than loudly.
